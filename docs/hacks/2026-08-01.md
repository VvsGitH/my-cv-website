# Hacks — audit of 2026-08-01

Workarounds currently in the tree. Each exists because a platform, a tool or a
test does not behave the way the straightforward code would assume. None is a
bug today; all of them are code that has to be defended rather than read.

Logged during the documentation cleanup, so the comments defending them could be
cut to one line without losing the record. **This is a to-do list for a later
corrective pass, not documentation** — a hack that gets removed should be struck
from here, and a hack that turns out to be permanent should graduate into an ADR.

Format per entry: what the platform does · what we do instead · what it would
take to remove.

---

## 1. `.drawer:not([open]) { display: none }` must beat the UA stylesheet

`src/components/chrome/drawer.css`

The author `display: flex` on `.drawer` (needed so the panel's children cover
its whole box, for the light dismiss) outranks the UA sheet's
`dialog:not([open]) { display: none }`. Without an explicit re-statement the
**closed** panel paints a full-height cream column over Sheet 1 — including in
the PDF, where it would not change the page count, so `assertTwoA4Pages()`
passes and the corruption ships silently.

**Remove when:** the panel no longer needs `display: flex` on the dialog element
itself — e.g. if `closedby` lands and the light dismiss stops depending on the
dialog's own box being fully covered.

## 2. `::-webkit-scrollbar` duplicated beside `scrollbar-width`/`scrollbar-color`

`src/components/chrome/drawer.css`

Two syntaxes for one scrollbar, because they have no common ancestor: the
standard pair, and the WebKit pseudo-elements Safari still answers to.

**Remove when:** Safari supports `scrollbar-width`/`scrollbar-color`.

## 3. The scroll lock `showModal()` does not apply

`src/components/chrome/drawer.css`

A modal `<dialog>` does **not** lock document scroll: measured in Chrome 150,
a trusted `PageDown` scrolled the page 700px behind an open modal. The HTML
Standard's rendering rules for `dialog:modal` set properties on the *dialog* and
say nothing about the document. So the lock is authored:
`html:has(.drawer[open]) { overflow: hidden }`, plus `scrollbar-gutter: stable`
in Reading Mode to stop `overflow: hidden` reclaiming the scrollbar's width and
re-wrapping every line behind the panel.

**Remove when:** the platform locks scroll for modal dialogs, or a standard
opt-in appears. ADR-0008 carries the measurement.

## 4. The `matchMedia` guard closes the panel directly, bypassing the signal

`src/components/chrome/Drawer.tsx`

An **open** modal forced to `display: none` keeps `open === true`, keeps
matching `:modal`, and keeps the document blocked — a dead page with nothing on
screen and no way out. So crossing into Paper Mode calls `panel.current?.close()`
directly rather than writing the signal, because going through the signal would
let the panel survive a render frame.

**Remove when:** never, probably — but it is a sharp edge that reads as
redundant state management and will be "simplified" by someone. Worth a comment
that survives.

## 5. The font wait has to come *after* hydration in the test helper

`tests/support/page.ts`

Chrome requests a face only when rendering needs it, so `document.fonts.ready`
resolves over the faces requested *so far*. The Toolbar's glyphs are only drawn
once the island hydrates, so waiting for fonts before hydration leaves a window
where the header Block measures ~2px short on fallback metrics instead of its
real `--header-height` — which drops Main's first heading by that much and fails
`paper.spec.ts`.

**It only reproduces under the load of the full suite**, which is what stretches
hydration out. That makes it a flaky test papered over by ordering.

**Remove when:** the header's height stops being a hard-coded measurement
(see 6), which is the real dependency.

## 6. `--header-height` is a hard-coded manual measurement

`src/styles/tokens.css`

`166.72px`, measured by hand off the rendered header Block, and one of the five
inputs to `--main-first-heading-gap`. It is content-derived, not geometry, so it
silently goes stale whenever the header's text or type changes — and the failure
is the two columns' first headings falling out of alignment.

Currently mitigated by an E2E assertion (ADR-0010) rather than fixed.

**Remove when:** the two columns can be aligned without it. ADR-0011 records why
subgrid was rejected — and that rejection has since expired, now that both
columns take one `--sheet-pad-block-start`. Tracked in `docs/todos/`.

## 7. The capture script's viewport and image-decode dance

`scripts/render-captures.mjs`

Two workarounds for silent capture corruption, both fully described in ADR-0009:
the viewport must be set to ≥ 53.5rem *before* `goto` or two embedded fonts are
never requested; and every image must be `decode()`d explicitly because Astro's
`<Image>` is `loading="lazy"` and the print pass outruns the network.

**Remove when:** `page.pdf()` can be told to request every declared face, and the
portrait is `loading="eager"` as a page decision.

## 8. The bare `@layer` statement must precede the `@import`s

`src/layouts/BaseLayout.astro` — **verify this is still live**

Placed after the imports, the production CSS minifier hoists the layer statement
in a way that reorders effective layer precedence. The failure is
**minifier-only**: dev looks correct and the built site does not.

`src/styles/global.css` appears to carry no bare statement at all, so the first
job here is to establish whether the hazard is currently present or already
sidestepped.

**Remove when:** the minifier stops reordering, or the layer order is expressed
somewhere it cannot hoist.

## 9. The column-prefix specificity workaround

`src/components/structure/Sheet.astro`

A rule needs its column class as a prefix purely to win a specificity contest
against a scoped rule, because Astro's scoping adds an attribute selector.
Without the prefix the first section gains an unwanted gap.

**Remove when:** the two rules stop overlapping, or the gap moves to the
component that owns it.

## 10. `@media (hover: hover)` gating on the Toolbar's controls

`src/components/chrome/toolbar.css`

A tap leaves `:hover` stuck on the control a phone visitor last touched, which
reads as a selected state it is not.

**Remove when:** never realistically — this is the standard remedy. Listed
because it is a platform wart, not because it is wrong.

## 11. `devtools: true` to make hydration mismatches visible

`astro.config.mjs`

A Preact hydration mismatch stops hydrating and re-renders **in silence** —
Preact logs nothing unless `preact/debug` is loaded. The integration runs with
`devtools: true` purely so the failure is observable.

**Remove when:** Preact warns on mismatch by default.
