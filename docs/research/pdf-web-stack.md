# Web tech stack for an A4 CV site with build-time PDF pre-rendering

Research date: 2026-07-24. All claims cite PRIMARY sources (official docs, specs, source repos, or the font foundry/designer). Blog posts are deliberately excluded.

## Recommendation (TL;DR)

**Stack: Astro (static output) + Playwright (headless Chromium `page.pdf()`) for the build-time PDF, deployed as static files to GitHub Pages.**

- **Framework — Astro, `output: 'static'` (the default).** Astro prerenders the whole site to plain HTML at build time with no server runtime and no client JS unless you opt in, which is exactly right for a content-light, minimal-JS A4 CV that must host cheaply on GitHub Pages ([Astro rendering modes](https://docs.astro.build/en/basics/rendering-modes/)). A single Astro component (or an "island" React/Solid component if you prefer JSX) is the one source of truth that renders both the live page and the page the headless browser captures. Content lives in separate `.md`/`.json`/`.ts` data files consumed by that component, satisfying the "content separate from layout" requirement. Vite+React (SPA) and Next.js `output: 'export'` both work, but Astro ships the least JS by default and is the most static-native of the three.
- **PDF tooling — Playwright over Puppeteer, marginally.** Both wrap the *same* Chromium print pipeline and expose the same knobs (`format: 'A4'`, `printBackground`, `preferCSSPageSize`, `margin`, `@media print` via `print` media default, page-break CSS). Playwright wins on CI ergonomics: one command (`npx playwright install --with-deps`) provisions the browser *and* its OS dependencies ([Playwright CI](https://playwright.dev/docs/ci-intro)). Puppeteer is an equally valid choice — it auto-downloads Chrome for Testing on install ([Puppeteer installation](https://pptr.dev/guides/installation)). Either way, **`page.pdf()` only works in headless Chromium** (see Q1).
- **Determinism — do not rely on the browser alone.** Chromium embeds a wall-clock `CreationDate`/document ID in the PDF, so two builds are not byte-identical out of the box. Load fonts to completion with `await document.fonts.ready` before capture, then post-process the PDF with `qpdf --deterministic-id` (and set `SOURCE_DATE_EPOCH`) to strip time-derived bytes (see Q2).
- **The A4 box — drive size from CSS `@page { size: A4 }` + `preferCSSPageSize: true`,** and size the on-screen "paper" in physical `mm` units, scaling responsively with CSS `transform: scale()` rather than changing the mm dimensions (see Q4).
- **Fonts — Lato and "Now" are free (SIL OFL); Garet is commercial** and must be purchased/self-hosted from Type Forward / TypeType (see Q6).

## Q1 — Headless PDF tooling: Puppeteer vs Playwright `page.pdf()`

Both tools drive Chromium's DevTools `Page.printToPDF`, so the feature set is nearly identical. Key facts from the official APIs:

**Headless-Chromium-only.** Playwright's `page.pdf()` is Chromium-only, and the API throws on other browsers/modes; the canonical error string is *"Page.pdf: PDF generation is only supported for Headless Chromium"* ([microsoft/playwright-python issue #2909](https://github.com/microsoft/playwright-python/issues/2909)). Puppeteer's `page.pdf()` likewise runs through the Chromium print path ([Puppeteer `page.pdf()`](https://pptr.dev/api/puppeteer.page.pdf)). Firefox/WebKit are out for PDF.

**A4 sizing.** Both accept `format: 'A4'` (Puppeteer default is `letter`) ([Puppeteer `PDFOptions`](https://pptr.dev/api/puppeteer.pdfoptions); [Playwright `Page.pdf()`](https://playwright.dev/docs/api/class-page)). Better for this project: set `@page { size: A4 }` in CSS and pass **`preferCSSPageSize: true`**, which makes the CSS `@page` size win over `format`/width/height (default `false`, which scales content to the paper) — same option name and semantics in both ([Puppeteer `PDFOptions`](https://pptr.dev/api/puppeteer.pdfoptions); [Playwright `Page.pdf()`](https://playwright.dev/docs/api/class-page)).

**`printBackground` / color adjust.** `printBackground` defaults to `false` in both; set it `true` to keep background graphics ([Puppeteer `PDFOptions`](https://pptr.dev/api/puppeteer.pdfoptions); [Playwright `Page.pdf()`](https://playwright.dev/docs/api/class-page)). Both docs additionally warn that `page.pdf()` "generates a pdf with modified colors for printing" and tell you to use the `-webkit-print-color-adjust` CSS property to force exact colors ([Playwright `Page.pdf()`](https://playwright.dev/docs/api/class-page); [Puppeteer `page.pdf()`](https://pptr.dev/api/puppeteer.page.pdf)).

**`@media print` handling.** By default `page.pdf()` renders with the **`print`** CSS media type, so your `@media print` rules apply automatically. To capture the `screen` rendering instead, call `page.emulateMediaType('screen')` (Puppeteer) / `page.emulateMedia({ media: 'screen' })` (Playwright) before `page.pdf()` ([Puppeteer `page.pdf()`](https://pptr.dev/api/puppeteer.page.pdf); [Playwright `Page.pdf()`](https://playwright.dev/docs/api/class-page)). For a pixel-perfect-vs-desktop CV, keep the paper styles identical in `screen` and `print` (or emulate `screen`) so there is one visual result.

**Page breaks.** Break control is pure CSS fragmentation — `break-before` / `break-after` / `break-inside` (and legacy `page-break-*`) — honored by Chromium's print engine; there is no tool-specific API for it. Use `break-inside: avoid` on the aside/blocks and `break-before: page` at the boundary between the two A4 pages. (Spec: [CSS Fragmentation / Paged Media Level 3](https://www.w3.org/TR/css-page-3/).)

**Header/footer & margins.** Both support `displayHeaderFooter` (default `false`) with `headerTemplate`/`footerTemplate` that accept injectable classes (`date`, `title`, `url`, `pageNumber`, `totalPages`), plus a `margin` object (default: no margins) ([Puppeteer `PDFOptions`](https://pptr.dev/api/puppeteer.pdfoptions); [Playwright `Page.pdf()`](https://playwright.dev/docs/api/class-page)). Note Playwright's caveat that page styles are not visible inside header/footer templates and script tags inside them are not evaluated ([Playwright class-page source](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/api/class-page.md)). For a CV you generally want **no** browser header/footer (leave `displayHeaderFooter: false`) and zero margins, letting the two A4 page components own all layout.

**Determinism of the raw output.** Neither API guarantees byte-stable output; both embed Chromium metadata. Puppeteer exposes experimental `tagged` (accessible/tagged PDF, default `true`) and `outline` (default `false`) options ([Puppeteer `PDFOptions`](https://pptr.dev/api/puppeteer.pdfoptions)) — worth pinning explicitly so a Puppeteer version bump doesn't flip a default and change bytes. See Q2 for making output reproducible.

**Verdict:** feature-parity for this job; pick **Playwright** for the smoother `--with-deps` CI install, or **Puppeteer** if you want the browser auto-bundled with zero extra flags.

## Q2 — Font embedding & determinism

**Guaranteeing fonts are loaded before capture.** Use the CSS Font Loading API: `document.fonts.ready` is a `Promise` (the `FontFaceSet.ready` property) that resolves only once the document has finished loading fonts and layout is complete and no further font loads are pending ([MDN `FontFaceSet.ready`](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/ready); [MDN `Document.fonts`](https://developer.mozilla.org/en-US/docs/Web/API/Document/fonts)). In the build script, after `page.goto(...)` run `await page.evaluate(() => document.fonts.ready)` before `page.pdf()`. Caveat from MDN: the set of *used* fonts can differ from *declared* fonts when `font-display: optional` fonts fail to load in time — so avoid `font-display: optional` on the CV fonts; prefer `font-display: block`/`swap` and, since this is offline rendering, self-host the woff2/ttf so there is no network race.

**Ensuring they embed (subset) into the PDF.** Chromium's print pipeline subsets and embeds the fonts actually used on the page, so as long as the glyphs are rendered (which `document.fonts.ready` guarantees) they are embedded in the output PDF; self-hosting the font files (rather than a remote CDN) removes network flakiness from the build.

**Sources of non-determinism and how to neutralize them.** PDFs "can contain metadata, object ordering, compression choices, and timestamps that change even when the pages look identical" ([reproducible-builds.org — Archives](https://reproducible-builds.org/docs/archives/)). Concretely, Chromium writes a wall-clock `CreationDate` and a time/filename-derived document ID, so successive builds differ byte-for-byte. Neutralize with a two-step approach:
1. **Pin the clock.** Set the widely-recognized `SOURCE_DATE_EPOCH` environment variable to a fixed value so time-derived fields are stable ([reproducible-builds.org — Timestamps / SOURCE_DATE_EPOCH](https://reproducible-builds.org/docs/timestamps/)).
2. **Normalize the PDF.** Post-process with **qpdf**: `--deterministic-id` "generate[s] a secure, random document ID using deterministic values. This prevents use of timestamp and output file name information in the ID generation," and `--newline-before-endstream` aids PDF/A-style reproducibility ([qpdf CLI docs](https://qpdf.readthedocs.io/en/stable/cli.html)). qpdf's own caveat: different qpdf *versions* may emit slightly different bytes, so pin the qpdf version in CI. Also explicitly set Puppeteer's `tagged`/`outline` (Q1) so defaults can't drift.

Result: `document.fonts.ready` → `page.pdf()` → `qpdf --deterministic-id` under a fixed `SOURCE_DATE_EPOCH`, with pinned browser + qpdf versions, gives byte-stable output across builds.

## Q3 — Framework fit (Astro vs Vite+React vs Next.js static export)

All three can produce a purely static site and can run a headless-render step in the build (it is just a Node script invoked after the framework's build emits HTML). Differences that matter here:

- **Astro — best fit.** Static is the default: "By default, your entire Astro site will be prerendered," producing real HTML files hostable on "any basic web server or CDN," with the guidance to "Start with the default 'static' mode until you are sure that most or all of your pages will be rendered on demand" ([Astro rendering modes](https://docs.astro.build/en/basics/rendering-modes/)). It ships zero JS by default and lets you embed a React/Solid island only if you want interactivity (e.g. the mobile drawer). Cleanest "one component → both live page and PDF-captured page" story, and content-in-separate-files is idiomatic (Astro content collections / `.md` / data files).
- **Vite + React — fine, slightly more DIY.** `vite build` outputs a `dist/` of optimized static assets you "may deploy to any of your preferred platforms," with documented GitHub Pages setup (set `base`, build, upload `dist`) ([Vite static deploy](https://vite.dev/guide/static-deploy/)). As an SPA it ships more client JS than Astro and you own the prerender-to-HTML wiring yourself (or add a plugin). Good if the owner wants a plain React component as the single source.
- **Next.js `output: 'export'` — works, heavier.** Setting `output: 'export'` makes `next build` emit an `out/` folder of static HTML/CSS/JS deployable to "any web server that can serve … static assets," with an official GitHub Pages template; but many features are unsupported in export mode (ISR, image optimization with the default loader, server actions, headers/redirects/rewrites, dynamic server functions) ([Next.js static exports](https://nextjs.org/docs/app/guides/static-exports)). For a two-page CV that's a lot of framework for little benefit.
- **SolidJS / Angular (briefly).** SolidStart and Angular (with prerendering) can both emit static output, but neither adds anything over Astro for this use case; Angular in particular is the heaviest option for a two-page static CV. Mention only — not recommended here.

**Verdict:** **Astro (static)**. Vite+React is the acceptable runner-up if a plain React component is strongly preferred; Next.js export is overkill.

## Q4 — The A4-in-HTML technique

**Print/PDF side.** Declare the page geometry in CSS Paged Media: `@page { size: A4; margin: 0 }`. Per the W3C spec, the `size` property "specifies the target size and orientation of the page box's containing block," and the `A4` keyword is "Equivalent to the size of ISO A4 media: 210 mm wide and 297 mm high"; you may equivalently give two explicit lengths, e.g. `size: 210mm 297mm` ([CSS Paged Media Module Level 3 — `@page`/`size`](https://www.w3.org/TR/css-page-3/); [MDN `@page`](https://developer.mozilla.org/en-US/docs/Web/CSS/@page)). Combined with Puppeteer/Playwright `preferCSSPageSize: true` (Q1), this makes the PDF page exactly A4 with no scaling drift.

**Screen side.** Give each "paper" element fixed physical dimensions in **mm** — `width: 210mm; height: 297mm` — so the on-screen box matches the print box 1:1. Use `mm`/`cm` rather than `px` because pixel sizing drifts with device DPI, whereas physical units stay consistent across browsers and print devices (principle stated in the [W3C Paged Media spec](https://www.w3.org/TR/css-page-3/) and reflected in [MDN `@page`](https://developer.mozilla.org/en-US/docs/Web/CSS/@page)). Note the spec's reminder that `@page` size is *not* the same as the `width`/`height` of your `body` element — `@page` sits outside the DOM and contains it — so you set both: `@page` for the sheet, and the mm-sized element for the on-screen paper.

**Responsive scaling without changing the mm box.** Keep the 210×297mm element's intrinsic size constant and scale the *whole* paper with `transform: scale(var(--k))` (and a matching wrapper height) or a CSS container query, so desktop shows two sheets side-by-side and mobile shows one shrunk-to-fit sheet. Never rewrite the mm dimensions per breakpoint — that is what causes layout to diverge between screen and PDF. The aside → left slide-in drawer on mobile is a separate responsive concern layered on top and can be excluded from the `@media print` / captured rendering.

## Q5 — Running headless Chromium in CI (GitHub Actions)

The build's PDF step needs a headless Chromium and its Linux shared-library dependencies on the runner.

- **Playwright:** it downloads and manages its own browser binaries; in CI you add one step — `npx playwright install --with-deps` — where `--with-deps` also installs the required OS packages, so nothing else is needed on the runner ([Playwright CI](https://playwright.dev/docs/ci-intro)).
- **Puppeteer:** installing the `puppeteer` package "automatically downloads a recent version of Chrome for Testing" (`puppeteer-core` does not download and requires you to point at a browser) ([Puppeteer installation](https://pptr.dev/guides/installation)). On a bare Linux runner you may still need to install Chrome's system libraries yourself (Playwright's `--with-deps` bundles that convenience; Puppeteer leaves OS deps to you).

Either way, run the headless render as a post-build Node script inside the same GitHub Actions job that runs the framework build, then upload the static output (plus the generated `.pdf`) to GitHub Pages.

## Q6 — Font availability & licensing (Garet, Now, Lato)

- **Lato — FREE, SIL Open Font License 1.1.** Designed by Łukasz Dziedzic and published by his foundry tyPoland with Google's support; the font software is licensed under the SIL OFL v1.1 ([latofonts.com — official site](https://www.latofonts.com/); [Font Squirrel — Lato](https://www.fontsquirrel.com/fonts/lato)). Free to self-host and embed via `@font-face` and available on Google Fonts ([Google Fonts — Lato](https://fonts.google.com/specimen/Lato)).
- **"Now" (Alfredo Marco Pradil) — FREE / open source.** The designer publishes it as "Now — Open Source Typeface" and states "Now Typeface is an Open Source font," distributed in 12 styles (regular + Alt weights) ([designer's page](https://alfredomarcopradil.com/now-open-source-typeface)); redistributors list it under SIL OFL v1.1 ([Font Library — Now](https://fontlibrary.org/en/font/now)). Free to self-host/embed. **Caution:** "Now" is a common typeface name — confirm the specific cut the CV uses is this OFL "Now" and not a same-named commercial family before shipping.
- **Garet — COMMERCIAL (must purchase / self-host).** A geometric sans by Mirela Belova & Stan Partalev, published by Type Forward and sold through TypeType/MyFonts/Fontspring; commercial use and webfont embedding require a purchased license, and webfont licenses are typically limited to a single domain ([TypeType foundry](https://typetype.org/); [TypeType licensing](https://typetype.org/licensing/); [MyFonts — Garet](https://www.myfonts.com/collections/garet-font-type-forward)). A limited free trial weight is distributed via Font Squirrel ([Font Squirrel — Garet](https://www.fontsquirrel.com/fonts/garet)), but do not assume the full family or unrestricted webfont rights are free — verify the exact EULA for the weights you embed. **This is the one licensing risk in the stack.**

1. ~~**Garet license cost.**~~ **Resolved — by substitution, the option named here.** Garet, Now and Lato were all dropped for **JetBrains Mono** and **Atkinson Hyperlegible**, both SIL OFL, with the licence files committed beside the fonts (ADR-0020). Nothing in the stack needs buying. One residue: **Primera Signature**, the signature face, has no licence on record, and its full `.ttf` is now committed to a public repo — a smaller version of the same question, accepted knowingly.
2. ~~**"Now" identity check.**~~ **Moot** — "Now" is no longer in the stack.
3. **True byte-stability is version-locked.** Reproducibility holds only if the Chromium/Playwright/Puppeteer *and* qpdf versions are pinned; a browser upgrade can change subsetting/compression and thus bytes even with `--deterministic-id` + `SOURCE_DATE_EPOCH`. Add a CI check that re-renders and diffs the PDF.
4. **Pixel-perfect screen-vs-PDF.** `page.pdf()` uses `print` media by default; if the live site's paper look lives under `@media screen`, either mirror those rules into `print` or `emulateMedia({ media: 'screen' })` before capture — otherwise the PDF and desktop rendering can diverge.
5. **Tagged-PDF default drift (Puppeteer).** `tagged` defaults to `true` and is marked experimental; pin `tagged`/`outline` explicitly so a library bump can't silently change the output.
6. **mm↔device rounding.** Even with mm units, sub-pixel rounding at the sheet edges can shift a page break by a line; validate the 2-page boundary visually in the generated PDF, and use `break-before: page` rather than relying on content height alone.
